# Day 008 — Guarded execution boundary

**Date:** 2026-11-03  
**Scope:** Request-bound dispatch capabilities, final adapter authorization, approval-claim binding, and fail-closed behavior.

## Objective

Move one security check from the gateway's control flow into the execution adapter boundary. A previous policy decision or a UI approval is not, by itself, sufficient evidence to call the configured tool adapter.

## Delivered

- Added a short-lived `DispatchPermit` bound to the canonical digest of the exact `ActionRequest`.
- Added an HMAC-SHA256 signature over request digest, dispatch mode, approval ID, issue/expiry timestamps, and a random nonce.
- Set the prototype permit lifetime to 15 seconds.
- Added a one-time nonce consumer with an atomic in-process lock, expiry pruning, and a bounded active replay cache (100,000 entries). Cache-capacity exhaustion fails closed.
- Wrapped the configured execution delegate in `GuardedExecutionAdapter`; the gateway now passes a permit for both ALLOW and approval-backed dispatch.
- Added `RegisteredToolAdapter`, an exact `(action, resource)` handler registry. The mock delegate uses only `read_database/research_db` and `send_email/company_email` bindings; unknown pairs fail closed even when the mock adapter itself is called directly.
- Re-evaluated current policy inside the adapter immediately before calling the delegate.
- For approval-backed dispatch, verified that the exact SQLite approval is in `executing` state and that the stored request digest, Agent, Action, Resource, and Request ID match.
- Converted an adapter-boundary authorization rejection on the normal ALLOW path into a recorded BLOCK result rather than allowing the request to proceed.
- Added tests for missing/forged/malformed permits, request-payload substitution, expiry, sequential and concurrent replay, policy revocation at dispatch, last-moment policy changes returning BLOCK, fake approval IDs, mismatched approval/request binding, and direct unregistered action/resource calls against the mock tool registry.
- Updated the threat model, README, and Technology page to describe the new boundary and its remaining limitations.

## Verification boundary

The only configured execution delegate remains `MockExecutionAdapter`. No database, email provider, shell, agent framework, or external tool is connected.

The HMAC key is generated in process memory and changes on restart. The nonce cache is also process-local. This design does not protect against code execution inside the trusted gateway process, access to the underlying delegate, compromised host credentials, multiple uncoordinated workers, or a tool provider that offers a direct path around Custos. Python underscore-prefixed attributes are not a security sandbox.

A production integration still needs a separate tool-side trust boundary where agent code never receives raw tool credentials or a usable direct client, plus shared/durable replay state, key rotation, downstream idempotency, and reconciliation for uncertain outcomes.

## Next gates

1. Complete CI for this change set and record the test results.
2. Add an isolated tool-provider harness whose only callable interface is the guarded adapter; attempt alternate-path calls.
3. Add a real agent framework only after its raw tool clients and credentials can be withheld from agent code.
4. Design crash reconciliation and downstream idempotency before any external side-effecting tool is enabled.
