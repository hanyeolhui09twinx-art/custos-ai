# Day 015 — Read-only Security Operations

**Date:** 2026-11-03  
**Scope:** Reviewer-authenticated key-ring status and sanitized lifecycle-event visibility.

## Objective

Key lifecycle events existed in component-local audit files, but the only way to inspect them was to open those files directly. This milestone adds a bounded, read-only API and a browser view without turning key administration into a web action.

## Delivered

- Added reviewer-only `GET /v1/security/overview`.
- Added optional `component`, `event`, and `limit` query filters. The component filter applies to the event list while both Gateway and Provider status summaries remain visible. The maximum combined event count is bounded at 200.
- Added a sanitized read model in `keyring_audit.py`. It reads the current observed active/accepted key IDs from each component's SQLite lifecycle snapshot and reconstructs revoked IDs from verified key lifecycle events.
- The read model verifies the complete JSONL hash chain before returning events. Missing, invalid, or over-32-MiB audit files are reported separately; invalid/oversized logs do not produce events presented as trusted.
- The API allowlists only lifecycle event names and their safe fields. It does not return arbitrary audit payloads, request bodies, raw key bytes, or SHA-256 fingerprints.
- Added a bilingual `simulation-studio/security-ops.html` page. It connects to the local API with the reviewer token, shows Gateway and Provider snapshots, provides component/event/limit filters, and displays lifecycle events using text-only DOM rendering. The token is kept in page memory and can be cleared; the page has no key-management controls.
- Added `CUSTOS_PROVIDER_DB` and `CUSTOS_PROVIDER_AUDIT_LOG` configuration paths so the local API can inspect the exact provider database and audit file used by the separate provider process.
- Updated OpenAPI, README, sitemap, Developer Guide, Technology page, and the threat model.

## Verification

The API tests cover reviewer-only access, agent-token denial, current/accepted/revoked ID summaries, component/event filters, invalid filters and limits, exclusion of secret/fingerprint and unrelated audit data, and detection of a broken audit chain.

## Verification boundary

- The page reads each component's last observed SQLite snapshot. It does not inspect another process's live memory or automatically detect an environment-variable change before restart.
- The API must be configured with the same provider database and audit paths used by the provider. A missing path is shown as not tracked/missing rather than inferred.
- The API is loopback-only and CORS remains restricted to the official GitHub Pages origin. The static page is not a remote backend.
- Audit-chain verification is local and hash-based. It does not protect against a privileged host actor rewriting both the database and the complete audit file, and it is not remotely anchored or independently signed.
- This is a manual read-only viewer, not continuous monitoring, alerting, or a production Security Operations Center.
