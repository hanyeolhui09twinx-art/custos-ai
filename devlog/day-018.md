# Day 018 — OpenAI Agents SDK Mediation Adapter

**Recorded:** 03 November 2026  
**Scope:** Optional framework adapter, stable tool-call identity, reviewer-separated approval, and integration contract tests.

## What was added

Added an optional Python integration for the OpenAI Agents SDK, pinned to `openai-agents==0.24.0` in `requirements-agents.txt`. The adapter uses the SDK's `function_tool` runtime and injects `ToolContext` so each tool call can be tied to its SDK tool-call ID.

The adapter currently exposes three tools through `create_custos_agent()`:

- `read_research_database` submits `read_database` / `research_db` to the local Custos API. The configured policy returns ALLOW and the current provider executes only through `MockExecutionAdapter`.
- `request_company_email` submits `send_email` / `company_email`. The configured policy returns `HUMAN_APPROVAL`; the request is not executed at submission time.
- `execute_reviewer_approved_request` asks Custos to execute a previously approved request. The Agent has no Reviewer credential. The local gateway checks the approval state, original requester, expiry, and current policy before attempting dispatch.

The SDK tool-call ID is SHA-256 transformed into a bounded Custos `request_id`, preserving idempotency when the same SDK tool call is replayed. Replays of an existing pending email approval return the same approval ID rather than creating a duplicate approval.

Added a loopback-only `CustosClient`, an example runner at `examples/openai_agents_sdk_custos.py`, optional dependency pin, developer-page instructions, and CI coverage for the SDK runtime.

## Enforcement boundary and remaining work

This adapter mediates only the three function tools returned by `create_custos_agent()`. It does **not** automatically mediate other tools or execution surfaces added to an Agent or process, including hosted tools, MCP, shell/computer tools, handoffs, raw functions, direct network access, or code execution. Those need independent server-side enforcement and adapter-specific tests. A function tool's prompt instructions are not a security boundary.

The example model invocation has not been run with a real OpenAI API key. No real database, email provider, or external tool is connected; all successful dispatch results remain simulated. The local API is loopback HTTP with development Bearer credentials and a shared Reviewer credential. This is a framework integration prototype, not a production security or isolation guarantee.

## Publication boundary

The integration remains in draft PR #2. The default branch and public GitHub Pages deployment have not been changed. The next engineering gate is to prove mediation at one actual tool-provider boundary and test bypass attempts against that boundary, rather than adding more framework wrappers and assuming they cover every route.
