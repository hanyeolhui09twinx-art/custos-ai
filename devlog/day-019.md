# Day 019 — Provider-Side Tool Authorization Registry

**Date:** 2026-11-03  
**Scope:** Local prototype / separate mock Provider process

## Change

Added a Provider-owned, deny-by-default registry that independently binds three dimensions:

- `research_agent` + `read_database` + `research_db` → `ALLOW`
- `research_agent` + `send_email` + `company_email` → `APPROVED`

The Provider no longer treats a valid HMAC permit as sufficient by itself. Before an execution receipt is claimed, it checks that the exact Agent/action/resource tuple is registered and that the signed permit uses the mode required for that tuple.

The Provider still uses the existing exact action/resource mock adapter. This additional registry adds the Agent identity and approval-mode checks at the downstream execution boundary.

## Adversarial coverage

Added a separate-process regression test that submits cryptographically valid, Gateway-signed permits for:

- `send_email` with `ALLOW` (mode escalation)
- `read_database` with `APPROVED` (incorrect approval mode)
- an unregistered database resource
- an unregistered Agent
- an unregistered audit-log action/resource

Every case is rejected with HTTP 403, and the test confirms that no Provider execution receipt is created for the rejected request. Existing tests continue to cover forged or missing permits, request substitution, key-ID substitution, nonce replay, cross-thread replay, restart persistence, idempotency conflicts, and indeterminate execution recovery.

## Security boundary and limitations

The Provider validates that an `APPROVED` permit was signed by a trusted Gateway key and that the request matches the Provider's registered mode. It does **not** independently query the Gateway's approval database, authenticate the human Reviewer's identity, or verify a separate Reviewer attestation. The Provider therefore still trusts the Gateway signer to issue `APPROVED` only after a valid human review.

The Provider remains a separate local OS process, not an OS sandbox or production isolation boundary. Its execution adapter remains mock-only. No real database, email system, or external tool credentials are connected. The prototype still lacks production TLS, independently managed reviewer identities, remote immutable audit storage, external security review, and full mediation of every Agent execution surface.

## Next engineering gate

Replace one mock operation with a narrowly scoped, read-only adapter behind this registry, define an explicit per-tool parameter schema, and test direct calls that attempt to escape that adapter's declared read-only scope. Then evaluate whether the Provider needs an audience-bound permit and an independently verifiable Reviewer attestation before any higher-impact integration.
