# Day 010 — Durable execution receipts and recovery

**Date:** 2026-11-03  
**Scope:** Provider-side idempotency, execution receipt persistence, interrupted-operation recovery, and lost-response reconciliation.

## Objective

Address the ambiguous outcome where a tool may have executed but the gateway did not receive its response. Never label an uncertain result as a definite BLOCK or success, and never repeat a possible side effect just to obtain a response.

## Delivered

- Added a provider-side SQLite `execution_receipts` ledger keyed by `(agent_id, request_id)`, with the exact request digest.
- The provider claims an `executing` receipt transactionally before calling its mock handler.
- On successful mock execution, the provider writes a durable `completed` result. An exact retry with a fresh valid permit returns that stored result instead of calling the handler again.
- Reuse of the same Agent/request ID with a changed digest returns an idempotency conflict.
- On provider startup, any leftover `executing` receipt is conservatively changed to `indeterminate`. Such a request is never automatically executed again.
- Added provider receipt lookup at `GET /v1/receipts/{agent_id}/{request_id}` for the loopback gateway client.
- Added the explicit `EXECUTION_UNKNOWN` outcome with `executed: null` when the provider may have received a request but its definite result did not reach the gateway.
- A same-ID retry now queries the provider receipt. A confirmed `completed` record resolves to the stored result; an active or indeterminate receipt remains unresolved. A missing receipt is not considered proof that the request was never accepted, and no automatic re-dispatch occurs.
- Added the same reconciliation path for approved executions whose HTTP response was lost.
- Added process integration tests for completed receipt replay, changed-payload conflicts, restart recovery of in-flight records, normal and approval-backed lost-response reconciliation, and provider outage uncertainty.

## Semantics and verification boundary

This is provider-local at-most-once invocation behavior, not an exactly-once guarantee for arbitrary external side effects. A crash can occur after a downstream tool succeeds but before the provider persists `completed`. The receipt then becomes `indeterminate`, even if the process stopped just before the tool call. That conservative state avoids duplicate automatic execution but may require manual investigation.

Real integrations still need a downstream idempotency key or operation-status query, explicit reconciliation, and a policy for unresolved receipts. Gateway request receipts also need independent crash-recovery work if the gateway itself terminates while a receipt is still marked `processing`. No real agent or external tool is connected.
