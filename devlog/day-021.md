# Day 021 — Versioned Provider Tool Contracts

**Date:** 2026-11-03  
**Scope:** Local prototype / Provider-side contracts / synthetic fixture + mock email

## Change

Added Provider-owned, versioned input/output contracts for the two registered tool bindings.

| Agent / action / resource | Contract | Permit mode | Result |
|---|---|---|---|
| `research_agent / read_database / research_db` | `research_query_v1` v`1.0.0` | `ALLOW` | `read_only` |
| `research_agent / send_email / company_email` | `email_request_v1` v`1.0.0` | `APPROVED` | `simulated` |

### Research contract

The input must contain exactly one field, `query`. It must be a non-empty string of at most 160 characters and resolve to 1–8 bounded search terms. The Provider reads at most five records from the synthetic SQLite fixture. The result contract checks the exact result keys, request identity, contract version, fixture marker, row count, and record shape.

### Email contract

The input must contain exactly `recipient`, `subject`, and `body`:

- Recipient: at most 320 characters, no whitespace/control line breaks, and a basic address format.
- Subject: 1–200 characters.
- Body: 1–8000 characters.

The operation remains mock-only. Even after approval, it returns `simulated`; it never sends email.

## Enforcement order

1. Resolve the exact Provider registration by Agent, action, and resource.
2. Validate the versioned input contract.
3. Verify and consume the signed Gateway permit.
4. Verify the permit mode required by the Provider contract.
5. Execute the allowlisted adapter.
6. Validate the versioned output contract.
7. Store the validated result in the durable execution receipt ledger.

Malformed input is rejected before permit consumption and before a receipt is claimed. A result that does not match the contract is not stored as a completed receipt.

## Adversarial coverage

Added or expanded tests for:

- Valid canonical email input and v`1.0.0` result version.
- Rejection of the legacy `to` field.
- Rejection of malformed recipient values and newline/header injection.
- Rejection of invalid semantic contract versions.
- No receipt creation for rejected input.
- SDK FunctionTool receipt includes the contract version.

## Limits

These are Provider-owned Python contracts. They are not published JSON Schema/OpenAPI tool schemas and do not establish interoperability with arbitrary tool servers. The email adapter is still simulated. Research reads remain confined to synthetic local data; no customer or external database is connected.

The Provider remains a separate local process on the same trusted machine, not an OS sandbox or production security perimeter. The Gateway signer remains trusted to issue `APPROVED` only after legitimate human review; the Provider does not independently authenticate Reviewer identity or read the approval database.

## Next engineering gate

Move the contracts to a standalone, machine-readable schema with generated validation tests, then add database-enforced least-privilege controls to any future real connector. Preserve the current deny-by-default registration and make contract version changes explicit and backward-compatible.
