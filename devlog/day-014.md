# Day 014 — Key compromise response and lifecycle audit

**Date:** 2026-11-03  
**Scope:** Detect key-ring changes at process startup, record lifecycle events, and document emergency revocation.

## Objective

Key-ring rotation could already be performed by changing environment configuration and restarting the gateway/provider, but the repository did not preserve a record of which key IDs were registered, activated, or removed between launches. This milestone adds local lifecycle observation without pretending that environment-based key management has become a live KMS or revocation service.

## Delivered

- Added `KeyRingLifecycle` in `keyring_audit.py`. Each component compares its configured ring with a persisted SQLite snapshot at startup.
- Gateway and provider each record their own key-ring state and append hash-chained JSONL lifecycle events.
- Added events for `DISPATCH_KEYRING_INITIALIZED`, `DISPATCH_KEYRING_LOADED`, `DISPATCH_KEY_REGISTERED`, `DISPATCH_KEY_ACTIVATED`, `DISPATCH_KEY_REVOKED`, and `DISPATCH_KEY_REPLACED`.
- The SQLite snapshot stores SHA-256 fingerprints solely to detect material replacement under an unchanged key ID. Audit events contain key IDs and change types only; raw key bytes and fingerprints are not written to the audit log.
- Added `--audit` to the provider CLI. When omitted, the provider writes a sibling audit file derived from its database path. The gateway continues to use its configured audit path.
- Added gateway-constructor and separate-provider process tests. The provider integration test removes a previously accepted key ID, restarts the provider, and confirms that a permit signed with the retired key is rejected with HTTP 403.
- Updated the Developer Guide, Technology status, README, and threat model with routine rotation and emergency compromise-response procedures.

## Emergency response sequence

1. Do not keep a compromised key in an overlap window.
2. Remove its ID from the provider's `CUSTOS_DISPATCH_KEYS` and restart the provider first. The provider is the acceptance boundary for dispatch permits and signed receipt reads.
3. Remove the compromised ID from every gateway configuration. Generate a fresh key under a new ID, update the provider and gateways, and restart every gateway.
4. Verify the provider and gateway audit files for the expected revoke/register/activate events.
5. Reconcile operations the provider may already have accepted using the same request ID and receipt. Revoking a key cannot undo an already accepted side effect; uncertain operations must not be replayed with a new ID.

The provider-first order is deliberate: an old gateway may temporarily continue signing with the compromised key, but the updated provider rejects it. Changing only the gateway first would not immediately stop an old gateway instance from using the compromised key.

## Verification boundary

- Lifecycle tracking begins when this feature is first deployed; it cannot reconstruct earlier key changes.
- This is startup configuration comparison, not a hot-reload watcher or a remote revoke API. Restart is required for config changes to take effect.
- Gateway and provider write separate local audit files. Hash chaining detects chain edits but does not make the files immutable or remotely anchored; a privileged host attacker can rewrite both the SQLite state and the log.
- Fingerprints are stored in local SQLite for change detection. No KMS/HSM, secure secret distribution, external secret vault, TLS, independent service identity, or third-party audit is added.
- Revocation rejects future provider verification for the removed ID. It does not reverse dispatch already accepted by the provider.
- The provider still runs mock tools only and remains a same-host loopback process, not an OS sandbox.
