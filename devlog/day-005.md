# Day 005 — Product experience and explanation

**Date:** 2026-11-03  
**Scope:** Homepage capability clarity, platform decision education, first-use journey, and API walkthrough.

## Objective

Improve the public product experience and the explanations together. A first-time visitor should understand the project's design, distinguish implemented behavior from simulation and future work, and know what to do next without assuming the prototype is already a production control product.

## Delivered

### Homepage: current capability status

Added a three-part status panel and labeled the hero architecture diagram explicitly as a conceptual target (not a live control console):
- **Implemented locally:** request validation, deny-by-default policy, ALLOW/HUMAN_APPROVAL/BLOCK decisions, approval expiry/single-use workflow, and local audit events.
- **Simulated:** homepage demo, browser Simulation Lab, and the Python MockExecutionAdapter. No real database read or email is performed.
- **Not yet integrated:** a real agent framework, real privileged tool adapters, direct-bypass resistance, and independent security review.

The panel links to the development-status page and Developer Docs.

### Platform: decision model and examples

Added three visually distinct decision cards:
- ALLOW — example: research_agent / read_database / research_db.
- HUMAN_APPROVAL — example: research_agent / send_email / company_email.
- BLOCK — protected or unlisted actions such as modify_custos_policy.

The page explains that a policy decision is not the same as execution: a BLOCK is a valid decision, HUMAN_APPROVAL pauses before execution, and ALLOW is still rechecked at dispatch.

### First-use navigation

Replaced the previous two-button product section with a responsive guided path:
1. Simulation Lab — explore predefined decisions in the browser.
2. Developer Docs — prepare the local Python API and temporary credentials.
3. Local Control Room — connect to the API after it is running locally.

The page now explains that GitHub Pages does not host the Python API.

### Developer Docs: end-to-end approval walkthrough

Replaced the partial reviewer snippet with one PowerShell walkthrough:
1. Submit send_email as the Agent.
2. Confirm HUMAN_APPROVAL and capture the returned approval_id.
3. List the pending queue and approve as Reviewer.
4. Execute once using the original Agent token and the required empty JSON body.

Added a visual response preview and an explicit explanation that HTTP 200 means the request was received and evaluated; it does not mean approval or external execution is complete. The execution result remains simulated.

### Responsive design and verification

Added responsive styles for the capability panel, policy-decision cards, guided journey, and API response preview. Added copy buttons to the PowerShell code samples, using the Clipboard API when available and selecting the code as a fallback. Extended the Node website checks to cover:
- Homepage capability status distinctions.
- Bilingual three-way policy explanations.
- Lab → Developer Docs → Local Control Room navigation.
- Complete send_email-to-approval walkthrough and expected response semantics.
- Code-copy controls, clipboard success feedback, and selection fallback wiring.

## Explicit limitations

- No real agent framework or privileged external tool has been integrated.
- The current Python execution adapter is a mock.
- The homepage and Simulation Lab remain browser simulations.
- CSS and source-level tests are not a substitute for manual visual review in real browsers and devices.
- A successful automated test run does not establish production security or resistance to agent bypass.

## Next gates

1. Manual visual review at desktop, tablet, and mobile widths.
2. Browser-to-loopback end-to-end test using the intended browser permission flow.
3. Real agent framework integration with tool calls mediated at the actual adapter boundary.
4. Direct-bypass, process-crash, retry, and partial-failure tests.
5. Independent security review before any production claim.
