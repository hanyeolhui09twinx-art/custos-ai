# Day 011 — Gateway restart recovery

**Date:** 2026-11-03  
**Scope:** Recovering interrupted gateway request receipts, reusing existing approvals, and reconciling approval-backed execution after process restart.

## Objective

The provider already stores durable execution receipts, but the gateway could still leave a local request receipt in `processing` if its own process exited. A retry then conflicted even when the provider had already completed the operation. Recover safely without creating duplicate approvals or dispatching another side effect.

## Delivered

- Added startup recovery for local gateway request receipts left in `processing`. They are changed to `indeterminate` with an explicit unknown-outcome response.
- A same-ID retry now checks for an existing request-bound approval before looking up the provider receipt.
- A pending or approved request returns the existing approval ID and state instead of creating a second approval.
- A provider-completed receipt restores the stored result to the gateway request receipt without redispatch.
- If the provider receipt is absent, mismatched, or indeterminate, the request remains `EXECUTION_UNKNOWN`; absence is not treated as proof that no dispatch occurred.
- Approved executions left in `executing` after a gateway crash now reconcile against the provider receipt even if the gateway had not yet persisted an `EXECUTION_UNKNOWN` response.
- Unclassified exceptions in the approved execution path now become `indeterminate` and remain eligible for same-ID reconciliation rather than being permanently labeled `failed`.
- Added four process integration tests for provider-completed recovery after gateway restart, unresolved restart with no provider receipt, recovery of an existing pending approval without duplicate creation, and approved execution recovery.
- The Local Control Room already locks request editing and new-ID generation while an outcome is unknown; the same-ID retry remains available to trigger reconciliation.

## Verification boundary

The recovery path assumes one gateway instance owns the local SQLite database. It does not implement leases or coordination between multiple gateway workers. If the gateway restarts before dispatch and no provider receipt exists, the request remains indeterminate even if no side effect occurred. This is intentionally conservative.

The provider remains a separate loopback process on the same trusted machine and still executes mock tools only. A completed receipt confirms completion within this mock provider. Real external tools still need downstream idempotency keys or an authoritative operation-status query to resolve the crash window between an external side effect and provider receipt commit.
