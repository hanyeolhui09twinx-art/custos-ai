# Day 009 — Separate mock tool-provider process

**Date:** 2026-11-03  
**Scope:** Separate-process dispatch, provider-side permit verification, durable replay rejection, and fail-closed transport behavior.

## Objective

Move the final mock tool registry out of the gateway process and test the signed dispatch hand-off across an actual local process boundary. This is a research harness, not a production isolation claim.

## Delivered

- Added `custos_provider.py`, a loopback-only HTTP service that owns the mock tool registry.
- Added `HttpToolProviderAdapter` so the gateway forwards the exact request and signed dispatch permit to the provider.
- Added a provider-side verifier that independently checks HMAC-SHA256 signature, exact request digest, mode/approval claim shape, timestamps, nonce format, and the 15-second validity window.
- Persisted consumed permit nonces in a provider-side SQLite table. A transaction plus a unique nonce primary key rejects concurrent replay and keeps replay claims after a provider restart.
- Kept the provider's only registered tools simulated. It has no real database client, email client, shell, cloud API, or external credentials.
- Added an optional local API configuration using `CUSTOS_TOOL_PROVIDER_URL` and `CUSTOS_DISPATCH_SIGNING_KEY`.
- Added separate-process integration tests for normal ALLOW and human-approved dispatch, missing/forged permit rejection, request substitution, concurrent replay, replay after provider restart, provider outage fail-closed behavior, and rejection of non-loopback endpoints.
- Updated developer documentation, the technology pipeline, README, and threat model to describe both the process boundary and its limitations.

## Verification boundary

The gateway and provider still run on the same trusted machine and share a development HMAC key through environment configuration. The provider uses loopback HTTP and has no independent OS sandbox, service account boundary, mutual TLS, key rotation, or credential vault. A local privileged attacker could inspect or alter either process. The provider checks the gateway's signed authorization capability; it does not independently evaluate a signed policy bundle.

The provider owns only mock handlers. There is no real agent framework and no external tool or credential connected. These tests establish behavior across two processes on one host; they do not prove that a malicious agent has no alternate path to a real tool.

## Next gates

1. Move the provider behind a dedicated OS/container boundary with a separate service identity and authenticated transport.
2. Integrate one real agent framework and prove the agent cannot access tool clients or credentials directly.
3. Add downstream idempotency and reconciliation for uncertain outcomes after tool success or network loss.
4. Design key rotation, policy versioning, request receipt recovery, and independent audit anchoring.
