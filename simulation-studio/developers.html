01 / BEFORE YOU START

실행 환경

현재 로컬 API는 Python 표준 라이브러리로 실행됩니다. 외부 패키지를 별도로 설치할 필요는 없지만, 브라우저 기반 Local Control Room을 사용할 때는 지원 브라우저의 Loopback 네트워크 권한이 필요할 수 있습니다.

RUNTIME

Python 3.10+

Python 3.10 이상. 기본 서버는 127.0.0.1:8765에 바인딩됩니다.

CREDENTIALS

Temporary tokens

Agent 및 Reviewer를 위한 임시 개발용 Bearer 토큰. 각 토큰은 32자 이상이어야 합니다.

EXECUTION

Mock adapter only

모든 외부 실행은 모의 처리됩니다. 데이터베이스 조회나 이메일 발송은 실제로 수행되지 않습니다.

Security Operations 열기 ↗
수동 키 회전 순서

먼저 제공자에 이전 키와 신규 키를 모두 등록합니다. 다음으로 모든 게이트웨이 발급기를 신규 CUSTOS_ACTIVE_DISPATCH_KEY_ID로 전환합니다. 구형 게이트웨이의 발급 가능성이 사라지고 15초 허가 수명과 배포 drain이 지난 뒤 양쪽 CUSTOS_DISPATCH_KEYS에서 이전 키를 제거하고 프로세스를 재시작합니다. 키 ID 제거가 폐기 동작입니다. 자동 만료·KMS·HSM은 구현되지 않았으며, 단일 키 환경 변수 CUSTOS_DISPATCH_SIGNING_KEY는 default 키 호환용으로 남아 있습니다.

긴급 키 유출 대응

일반 회전과 달리 유출이 의심되는 키에는 중첩 유예 기간을 두지 않습니다. 먼저 제공자 CUSTOS_DISPATCH_KEYS에서 손상된 ID를 제거하고 제공자를 즉시 재시작합니다. 제공자가 허가 검증의 수락 경계이므로 이 시점 이후 해당 ID의 기존 허가와 영수증 조회 서명은 거부됩니다. 다음으로 모든 게이트웨이 설정에서도 해당 ID를 제거하고, 새 키를 새 ID로 생성해 양쪽 프로세스를 갱신·재시작합니다. 게이트웨이만 먼저 바꾸면 오래된 게이트웨이가 구키로 서명할 수 있고, 제공자만 바꾸면 그 요청은 거부되므로 제공자를 먼저 갱신합니다. 게이트웨이와 제공자 감사 파일에서 DISPATCH_KEY_REVOKED, DISPATCH_KEY_REGISTERED, DISPATCH_KEY_ACTIVATED 이벤트를 확인합니다. 감사 로그에는 키 값이나 지문을 넣지 않습니다. 이미 제공자가 수락한 작업은 키 폐기로 되돌릴 수 없으므로 동일 request_id의 영수증으로 결과를 조정하고, 불확실한 작업을 새 ID로 재실행하지 않습니다. 이 기능은 프로세스 시작 시 로컬 설정 변화를 기록하며 실시간 폐기 API, 원격 감사 저장소, KMS/HSM은 제공하지 않습니다.

실행 결과 원장과 재시도 규칙

제공자는 Agent ID·request_id·요청 지문을 묶어 실행 결과를 SQLite에 기록합니다. 완료된 동일 요청은 저장된 결과를 반환하고 다시 실행하지 않습니다. 같은 ID에 다른 페이로드를 사용하면 충돌입니다. 실행 중 프로세스가 종료되면 해당 요청은 indeterminate로 남고 자동 재실행하지 않습니다. 게이트웨이가 응답을 받지 못하면 EXECUTION_UNKNOWN과 executed=null을 반환합니다. 같은 request_id로 다시 제출하면 제공자 원장을 조회해 완료 여부를 조정합니다. 영수증이 없다는 사실만으로 미실행을 단정하지 않으므로 새 ID를 만들어 재시도하지 마세요.

중요한 한계

제공자는 SQLite에 nonce 소비 기록을 영속화하고, 제공자 재시작 후에도 같은 허가의 재사용을 차단합니다. 그러나 두 프로세스는 같은 신뢰된 컴퓨터에서 실행되며, 제공자는 모의 도구만 실행합니다. 이는 OS 샌드박스나 운영용 격리, 실제 도구 권한 통제를 증명하지 않습니다. 키 수명주기 이벤트는 로컬 프로세스 시작 시에만 기록되며, 실시간 감시·원격 감사 저장소·KMS/HSM·상호 TLS·외부 자격증명 저장소는 구현되지 않았습니다.

03 / REQUEST MODEL

요청 형식

요청 주체는 Bearer 토큰에서 서버가 매핑합니다. 요청 본문에 agent_id를 직접 넣지 않습니다. 허용되는 필드는 action, resource, parameters, request_id입니다.

JSON / POST BODY02 — SUBMIT REQUEST
{
  "action": "read_database",
  "resource": "research_db",
  "parameters": {},
  "request_id": "docs-read-001"
}

request_id는 선택 사항이지만, 동일 작업의 재시도에는 같은 ID를 사용해야 중복 실행을 피할 수 있습니다. 같은 ID에 다른 페이로드를 넣으면 충돌로 거부됩니다. 매개변수는 JSON 객체여야 하며 민감정보 필드와 크기 제한이 적용됩니다.

POWERSHELL / HTTP REQUEST03 — SUBMIT AN ACTION
$payload = @{
  action = "read_database"
  resource = "research_db"
  parameters = @{}
  request_id = "docs-read-001"
} | ConvertTo-Json -Depth 10

Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:8765/v1/requests" `
  -Headers @{ Authorization = "Bearer $agentToken" } `
  -ContentType "application/json" `
  -Body $payload
Agent ID는 토큰에서 파생됩니다.

요청 본문에 agent_id를 보내지 않습니다. 서버가 Bearer 토큰을 설정된 Agent ID에 매핑합니다.

04 / API ROUTES

API 엔드포인트

GET /health를 제외한 엔드포인트는 Bearer 인증이 필요합니다. Agent 토큰은 요청 제출 및 본인 승인 요청 실행에 사용하고, Reviewer 토큰은 승인 목록 조회와 검토에 사용합니다.

이 예제는 현재 정책의 HUMAN_APPROVAL 경로를 처음부터 끝까지 따라갑니다. send_email 요청은 실제 이메일을 보내지 않고 승인 레코드만 생성합니다.

01Agent가 요청 제출send_email → HUMAN_APPROVAL
02승인 ID 확인요청 응답의 approval_id
03Reviewer 검토approve 또는 deny
04원래 Agent 실행승인된 요청 1회 실행 시도
POWERSHELL / HUMAN APPROVAL ROUNDTRIP04 — REQUEST → REVIEW → EXECUTE
# 1) Agent submits a request that requires human approval
$emailPayload = @{
  action = "send_email"
  resource = "company_email"
  parameters = @{}
  request_id = "docs-email-001"
} | ConvertTo-Json -Depth 10

$emailResponse = Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:8765/v1/requests" `
  -Headers @{ Authorization = "Bearer $agentToken" } `
  -ContentType "application/json" `
  -Body $emailPayload

# Confirm the policy outcome and capture the approval ID
$emailResponse
if ($emailResponse.decision -ne "HUMAN_APPROVAL" -or -not $emailResponse.approval_id) {
  throw "Expected HUMAN_APPROVAL with an approval_id."
}
$approvalId = $emailResponse.approval_id

# 2) Reviewer checks the pending queue
$pending = Invoke-RestMethod -Method Get `
  -Uri "http://127.0.0.1:8765/v1/approvals" `
  -Headers @{ Authorization = "Bearer $reviewerToken" }
$pending.approvals | Format-Table approval_id, status, expires_at

# 3) Reviewer approves the exact request
$reviewBody = @{ decision = "approve" } | ConvertTo-Json
$reviewResult = Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:8765/v1/approvals/$approvalId/review" `
  -Headers @{ Authorization = "Bearer $reviewerToken" } `
  -ContentType "application/json" `
  -Body $reviewBody
$reviewResult

# 4) The original Agent attempts execution once
# The API currently requires a JSON object body, even though it is empty.
$execution = Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:8765/v1/approvals/$approvalId/execute" `
  -Headers @{ Authorization = "Bearer $agentToken" } `
  -ContentType "application/json" `
  -Body "{}"
$execution
EXPECTED RESPONSE / POST /v1/requestsHTTP 200
{
  "decision": "HUMAN_APPROVAL",
  "executed": false,
  "approval_id": "generated-by-server",
  "request_id": "docs-email-001"
}

HTTP 200은 요청이 정상적으로 접수되고 판정됐다는 뜻입니다. 승인 완료나 외부 행동 실행을 뜻하지 않습니다. approval_id가 있어야 다음 Reviewer 단계로 진행할 수 있습니다.

이 흐름의 실행 어댑터는 MockExecutionAdapter입니다. 응답은 simulated 결과이며 이메일이 발송되지 않습니다. 실행 중 프로세스 충돌 시 자동 복구도 구현되어 있지 않습니다.

승인 단계는 요청 스냅샷과 연결됩니다. Reviewer는 승인 또는 거부할 수 있으며, 실행은 원래 요청한 Agent 토큰으로 한 번만 시도할 수 있습니다. 실제 실행 결과는 mock adapter의 시뮬레이션 응답입니다.

05 / APPROVAL LIFECYCLE

승인 상태의 생명주기

승인 레코드는 제한된 상태 전이를 가집니다. 만료 시각, 요청자 식별, 승인 스냅샷 무결성, 단일 실행 클레임을 각 단계에서 확인합니다.

STATETRANSITIONCONDITION
pendingapproved / denied / expiredReviewer가 승인·거부하거나 TTL 만료
approvedexecuting / expired원래 요청한 Agent가 만료 전 실행을 요청
executingexecuted / blocked / failed실행 어댑터 결과 또는 실행 직전 정책 재검사 결과

denied·expired·executed·blocked·failed는 종료 상태입니다. 현재 구현에는 실패 후 자동 재실행이나 프로세스 충돌 복구가 없습니다. 서버 중단 시 executing 상태가 남을 수 있으므로 운영 시스템으로 사용하면 안 됩니다.

06 / HTTP RESPONSES

응답과 오류 코드

정책 판정 결과와 HTTP 전송 오류는 구분해야 합니다. BLOCK 또는 HUMAN_APPROVAL은 요청을 정상적으로 판정한 결과이므로 일반적으로 HTTP 200 JSON 응답으로 반환됩니다.

선택형 Python 어댑터는 OpenAI Agents SDK의 function_tool을 사용합니다. 생성된 Agent에는 Custos API를 호출하는 함수만 등록됩니다. SDK가 도구를 호출하면 도구 호출 ID를 멱등성 request_id로 변환하고, 정책 판정·승인·실행은 로컬 Custos API가 처리합니다.

ALLOW / MOCK

read_research_database

read_database / research_db를 제출합니다. 현재 결과는 모의 실행이며 실제 데이터베이스를 읽지 않습니다.

HUMAN APPROVAL

request_company_email

send_email / company_email을 제출합니다. 승인 ID만 생성되며 Reviewer가 승인하기 전에는 실행되지 않습니다.

POST-REVIEW

execute_reviewer_approved_request

승인 ID로 실행을 요청합니다. 원래 Agent의 소유권, Reviewer 승인 상태, 만료, 현재 정책을 서버가 다시 확인합니다.

현재 gateway는 MockExecutionAdapter를 사용합니다. 검색 도구는 실제 데이터를 읽지 않고, 이메일 요청은 실제 발송되지 않습니다. 별도 Reviewer 자격 증명으로 승인한 뒤에만 원래 Agent가 승인 ID로 실행을 요청할 수 있습니다. CI는 모델 API를 호출하지 않고 SDK FunctionTool 런타임을 로컬 Custos 테스트 서버에 연결해 계약을 검증합니다.

이 어댑터만으로 모든 Agent 동작이 통제되는 것은 아닙니다.

create_custos_agent()가 생성하는 도구에만 적용됩니다. Hosted tools, MCP, Shell, Computer, handoff 또는 원시 함수를 추가하면 이 어댑터를 자동으로 통과하지 않습니다. 모든 특권 행동을 통제하려면 각 도구 제공자와 실행 서버 자체에서 Custos 권한 검사를 강제해야 합니다.
